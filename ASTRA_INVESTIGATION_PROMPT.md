## Context

You are auditing the full configuration of a personal CoreXy 3D printer running
Klipper + Moonraker. The repo is at `f:\dev\COREXY-config-cleanup` (Windows
workspace). Two documents already exist there and are your required starting
context — **read both in full before doing anything else**:

1. `HANDOFF.md` — full project history, hardware specifics, recent calibration
   work (rotation_distance, Z-offset, input shaper, pressure advance), known
   Klipper/Moonraker quirks, and the current outstanding task list.
2. `PRUSASLICER_PROFILE_REVIEW.md` — a completed parameter-by-parameter review
   of the PrusaSlicer printer/print/filament/physical_printer profiles. This
   covers the *slicer* side only. Your job extends this same exercise to the
   *firmware/Klipper config* side, and to double-check the slicer-side findings
   against real research rather than the prior model's unaided reasoning.

## Scope — which files are actually "live"

The Klipper config lives in `f:\dev\COREXY-config-cleanup\config\`. This folder
has a lot of historical clutter — **only audit the files actually loaded by the
live Klipper instance**. The include graph, per `config/printer.cfg`:

```
printer.cfg
├── mainsail.cfg
├── hardware.cfg        # steppers, TMC drivers, MCU, board pins
├── tuning.cfg          # motion tuning, input shaper, firmware retraction
├── thermistors.cfg     # extruder, bed heater, temperature sensors
├── fans.cfg            # part cooling, hotend fan, controller fan
├── probe.cfg           # BLTouch, bed mesh, leveling
├── advanced.cfg        # exclude_object, arcs, skew correction
├── system.cfg          # virtual SD, force_move, etc.
├── macro.cfg           # START_PRINT/END_PRINT and other operator macros
├── calibration.cfg     # user-facing calibration gcode wrappers
├── neopixel1.cfg        # LED status effects
├── menu.cfg            # mini12864 display + menu

```

**Explicitly ignore / do not treat as live config:**
- `calibration_ui.cfg` and `test_prints.cfg` — present in the repo but
  `printer.cfg` explicitly comments that they are retained for history only and
  are **not** included in the live config.
- Anything with a dated suffix (`printer-20251216_203649.cfg` and similar),
  `.backup`, `.before_cleanup`, `.before-split-*` suffixes, or the
  `config-20251214-133910.zip` archive — these are historical snapshots, not
  current config.
- The `#*# <---------------------- SAVE_CONFIG ---------------------->` block
  and everything below it at the bottom of `printer.cfg` is auto-generated by
  Klipper itself — read it for current calibrated values (bed mesh, etc.) but
  never hand-edit it or suggest hand-editing it.

Also read `generate_calibration_gcode.py` if relevant to any calibration macro
you're evaluating (it's a helper script, not a Klipper config file itself).

## What to actually do

1. **Read `HANDOFF.md` and `PRUSASLICER_PROFILE_REVIEW.md` in full first.** Do
   not duplicate ground already covered there — build on it.
2. **Go through every active `.cfg` file listed above, setting by setting**,
   the same way `PRUSASLICER_PROFILE_REVIEW.md` was done for the slicer side.
   For every non-trivial parameter, form an opinion on whether it's at a
   theoretically-ideal value for this specific hardware:
   - CoreXY kinematics, 300×300 bed, Z max 400
   - STM32F407 (SKR Pro-class) MCU + Raspberry Pi as a second "rpi" MCU
   - BLTouch probe (x_offset -27, y_offset -20)
   - ADXL345 accelerometer on Pi SPI0 CE0, input shaper currently 65.0Hz X /
     46.2Hz Y (mzv both), measured after belt retensioning
   - Bondtech BMG extruder, `rotation_distance` recently recalibrated to
     26.5475 after fixing physical filament slippage
   - `pressure_advance` currently just a placeholder (0.05), never actually
     tuned
   - `[printer]` motion limits: `max_velocity: 300`, `max_accel: 3000`,
     `max_z_velocity: 15`, `max_z_accel: 350`, `square_corner_velocity: 5.0`
   - Extruder TMC2209 has **no** `[tmc2209 extruder]` section at all (runs on
     board/UART default current) — a previous attempt to add one with
     `uart_pin: PD4` caused intermittent hard shutdowns
     (`Unable to read tmc uart 'extruder' register IFCNT`) and was reverted.
     Investigate whether this UART pin assumption was actually correct for
     this specific board, and whether there's a safer way to control extruder
     current (e.g., current-only config without UART readback, or confirming
     the correct UART pin from board documentation/firmware source).
3. **Actually research rather than reason from training data alone.** For each
   setting you're unsure about or want to challenge:
   - Check the official Klipper documentation (klipper3d.org) and the
     Klipper GitHub repo (`Klipper3d/klipper`) — `docs/Config_Reference.md`,
     relevant example configs in `config/`, and any relevant GitHub issues or
     discussions about this board/driver/probe combination.
   - Check community best-practice references where relevant (e.g. Ellis's
     print tuning guide, Voron/RatRig documentation) for things like input
     shaper accel limits, TMC current/stealthchop tuning, pressure advance
     methodology, probe safety margins.
   - Search GitHub for the specific board (SKR Pro or equivalent SKR Pro-class
     STM32F407 board) and BLTouch + ADXL345-on-Pi setups similar to this one,
     to sanity check pin assignments and known gotchas (e.g. the previously
     reverted TMC UART attempt).
   - Prefer primary sources (official docs, source code, maintainer comments)
     over random forum posts. Cite what you used.
4. **Flag concrete, actionable findings only** — not a restatement of every
   setting that's already fine. Things worth flagging:
   - Deprecated/removed Klipper config options still in use.
   - Missing recommended safety settings (e.g. `min_temp`/`max_temp` sanity
     margins, `idle_timeout`, endstop/homing safety margins, verify_heater
     tuning).
   - TMC2209 driver settings that don't match documented best practice for
     this current/voltage/motor combination (run_current headroom,
     stealthchop_threshold, hybrid/coolstep thresholds) for the steppers that
     *do* have `[tmc2209 ...]` sections — cross-check against actual motor
     specs if discoverable, not just assumed values.
   - Whether the configured `max_accel: 3000` is actually consistent with what
     the *measured* 65.0Hz X / 46.2Hz Y input shaper frequencies would
     recommend (Klipper's shaper calibration typically suggests a max
     recommended accel alongside the frequency — reconstruct/estimate this if
     possible and compare).
   - Any pin conflicts, inconsistent comments vs. actual values (e.g.
     `printer.cfg` has a stale comment claiming pressure_advance is "0.06"
     while the real value in `thermistors.cfg` is 0.05 — find any other drift
     like this).
   - Anything in `probe.cfg` (BLTouch config, bed mesh parameters) that
     deviates from documented best practice for probe reliability/accuracy.
   - Anything in `advanced.cfg` (exclude_object, arcs, skew correction) worth
     tightening.
   - Revisit the reverted extruder TMC2209 UART issue with fresh research —
     confirm or correct the wiring/pin assumption, and propose a concrete,
     specific next step (not just "verify wiring").

## Output requirements — this is important

**Do not modify any live Klipper config file, and do not push/deploy anything
to the printer.** This is a research-and-recommend pass only — the user will
review and apply anything approved manually or in a follow-up session.

All findings must be appended into `PRUSASLICER_PROFILE_REVIEW.md` (extend it
with new sections for the Klipper config side — keep the existing PrusaSlicer
content intact, add new top-level `##` sections below it, e.g.
`## Klipper Firmware Config Review — hardware.cfg`, etc., mirroring the
existing per-file/per-parameter table style).

**Every suggested change must be visually distinguished from the existing
review text using color**, since this doc will be read in VS Code's markdown
preview (which renders inline HTML/CSS in `.md` files). Use this exact pattern
for every new suggestion:

```html
<div style="color:#e67e22; border-left: 3px solid #e67e22; padding-left: 10px; margin: 8px 0;">

**Reasoning:** <why, with a citation/source link>.

</div>
```

Use `#e67e22` (orange) for suggested value changes, and `#c0392b` (red) for
anything you consider a genuine safety concern, using the same block style. If
you disagree with something the earlier PrusaSlicer review already flagged
(e.g. the `enable_dynamic_overhang_speeds` or `autoemit_temperature_commands`
findings), add your own colored block right after that existing entry rather
than editing the original text, so both opinions remain visible for the user
to compare.

End the document with a new `## Astra Research Summary` section listing every
suggested change in one place with a priority order (safety-relevant first),
plus a short "sources consulted" list of the specific docs/GitHub
pages/issues you actually referenced.
